# 주식 자동화 하네스 설계

상태: 승인됨

기준일: 2026-07-24

가격 데이터 공급자: KRX Open API

## 1. 목적

이 설계의 목적은 n8n, PostgreSQL, Gemini, Slack으로 구성된 주식 뉴스 자동화 프로젝트를 에이전트가 읽고 재현하고 검증할 수 있는 저장소 중심 시스템으로 전환하는 것이다.

첫 번째 제품 목표는 KRX 일별 OHLCV를 안정적으로 수집하고 14일 ATR을 계산한 뒤, 검증된 가격 데이터가 있을 때만 뉴스 감성 분석과 가격 신호를 결합하는 것이다. 운영 n8n 활성화, 운영 데이터베이스 변경, 실제 Slack 발송은 자동 수행 범위에 포함하지 않으며 사용자 승인 후 별도로 실행한다.

## 2. 설계 원칙

1. 저장소를 설계, 스키마, 워크플로, 테스트와 운영 절차의 기준점으로 사용한다.
2. 짧은 `AGENTS.md`는 규칙 전체가 아니라 관련 문서와 실행 명령을 안내하는 목차로 사용한다.
3. 외부 시스템의 응답은 신뢰하지 않고 경계에서 스키마와 값 범위를 검증한다.
4. 뉴스 감성 판단과 가격 계산을 분리한다. Gemini는 목표가, 손절가와 진입가를 결정하지 않는다.
5. 동일 입력을 다시 처리해도 결과가 중복되지 않도록 멱등성을 보장한다.
6. 성공 주장에는 같은 작업에서 실행한 검증 결과가 있어야 한다.
7. 비밀정보는 저장소, 테스트 fixture와 로그에 기록하지 않는다.
8. 에이전트는 읽기와 검증을 병렬화할 수 있지만 동일 파일과 동일 데이터 흐름의 쓰기는 직렬화한다.

## 3. 범위

### 포함

- 비밀정보를 제거한 현재 n8n export의 저장소 편입
- PostgreSQL 스키마와 마이그레이션의 버전 관리
- KRX 일별 OHLCV 수집 경계와 데이터 계약
- 종목별 최소 20거래일 보유 여부 검사
- 14일 ATR 계산
- 뉴스 정제, Gemini 응답 검증과 가격 데이터 결합
- `quant_market_news`와 `ai_signal_tracker`의 멱등 저장 정책
- 로컬 정적 검사, fixture 테스트와 격리 통합 테스트
- 실행 로그, 실패 상태와 재처리 절차
- 사용자 승인이 필요한 운영 경계

### 제외

- KIS Open API 연동
- 실시간 체결가와 호가 수집
- 자동 주문과 포지션 관리
- 운영 n8n workflow 자동 활성화
- 운영 데이터베이스 자동 마이그레이션
- 운영 Slack 채널 자동 발송
- 수익률을 보장하거나 투자 판단을 자동 집행하는 기능

KIS는 추후 실시간 시세 또는 주문 기능이 필요할 때 동일한 시장데이터 인터페이스의 추가 어댑터로 검토한다.

## 4. 저장소 구조

```text
AGENTS.md
ARCHITECTURE.md
workflows/
  n8n/
db/
  migrations/
  schema/
src/
  market_data/
  indicators/
tests/
  fixtures/
  workflow/
  integration/
scripts/
  verify.ps1
docs/
  decisions/
  runbooks/
  superpowers/
    specs/
    plans/
```

- `workflows/n8n`: 비밀값을 포함하지 않은 실제 n8n export를 보관한다.
- `db/migrations`: 적용 순서가 명확한 스키마 변경 SQL을 보관한다.
- `db/schema`: 검증된 현재 스키마 스냅샷과 데이터 계약을 보관한다.
- `src/market_data`: KRX 호출, 응답 검증, 정규화와 저장 경계를 담당한다.
- `src/indicators`: ATR 등 결정론적 지표 계산만 담당한다.
- `tests/fixtures`: 외부 호출 없이 재현 가능한 KRX, 뉴스와 Gemini 샘플을 보관한다.
- `scripts/verify.ps1`: 저장소 전체 검증의 단일 진입점이다.

## 5. 컴포넌트와 책임

### 5.1 KRX 수집기

입력은 종목코드와 조회 거래일 범위다. 출력은 정규화된 일별 OHLCV 레코드 목록이다.

각 레코드는 종목코드, 거래일, 시가, 고가, 저가, 종가, 거래량과 공급자 식별자를 가진다. 수집기는 인증정보를 환경변수 또는 n8n credential에서 읽으며, 원문 인증정보를 로그에 남기지 않는다.

수집기는 다음 값을 거부한다.

- 종목코드 또는 거래일 누락
- 시가, 고가, 저가, 종가 중 숫자가 아닌 값
- 음수 가격 또는 음수 거래량
- 고가가 시가, 저가 또는 종가보다 낮은 값
- 저가가 시가, 고가 또는 종가보다 높은 값
- 동일 응답 안의 중복 종목·거래일

휴장일의 빈 결과는 정상 무데이터로 처리한다. 인증 실패, 제한 초과, 응답 형식 변경과 네트워크 실패는 서로 다른 오류 코드로 분류한다.

### 5.2 OHLCV 저장소

종목코드와 거래일의 조합을 유일키로 사용한다. 동일 데이터의 재수집은 중복 행을 만들지 않는다. 기존 값과 새 값이 다른 경우 공급자 원본, 변경 시각과 변경 필드를 구조화 로그에 기록하고 정책에 따라 갱신한다.

시장데이터 저장과 Slack 알림은 같은 트랜잭션에 포함하지 않는다.

### 5.3 ATR 계산기

14일 ATR은 다음 순서로 계산한다.

1. 각 거래일의 true range를 `max(고가-저가, abs(고가-전일종가), abs(저가-전일종가))`로 계산한다.
2. 첫 ATR은 연속된 14개 true range의 산술평균으로 계산한다.
3. 이후 ATR은 Wilder 방식인 `(이전 ATR × 13 + 현재 true range) / 14`로 계산한다.

계산 대상 종목에 전일 종가를 포함한 충분한 연속 거래일 데이터가 없으면 ATR을 생성하지 않고 `INSUFFICIENT_HISTORY` 상태를 반환한다. 캘린더 날짜의 연속성은 요구하지 않으며 거래일 순서만 사용한다.

### 5.4 뉴스 수집과 정제

뉴스는 제목, 설명, 원문 링크와 게시 일시를 데이터 계약에 맞춰 정규화한다.

- 빈 결과를 가짜 뉴스 레코드로 바꾸지 않는다.
- `pub_date_kst`가 없거나 파싱되지 않으면 데이터베이스 삽입 전에 실패 항목으로 분리한다.
- `originallink`가 같은 뉴스는 동일 뉴스로 취급한다.
- 제목 기반 유사 중복 제거는 원문 링크 중복 제거 이후 적용한다.
- HTML 정제 후에도 원문 링크와 게시 일시는 유지한다.

### 5.5 Gemini 감성 분석

Gemini의 출력 범위는 각 뉴스의 `sentiment_score`와 `market_scenario`로 제한한다.

- `sentiment_score`는 -1.0 이상 1.0 이하의 숫자여야 한다.
- 출력 배열 길이는 입력 뉴스 배열 길이와 같아야 한다.
- 각 출력은 입력 뉴스의 안정적인 식별자와 연결되어야 한다.
- JSON 파싱 오류, 누락 필드와 개수 불일치는 실패 상태로 기록한다.
- 오류를 조용히 폐기하지 않으며 원문 전체 대신 실행 ID, 오류 유형과 입력 건수만 로그에 남긴다.

Gemini 출력에는 `target_price`, `stop_loss`와 `entry_price`를 요청하거나 저장하지 않는다.

### 5.6 가격 신호 계산

가격 신호 계산은 다음 선행조건을 모두 만족할 때만 실행한다.

- 종목별 최소 20거래일 OHLCV 존재
- 계산일의 유효한 종가 존재
- 유효한 14일 ATR 존재
- 연결된 뉴스 감성 결과가 데이터 계약을 통과

진입가, 목표가와 손절가의 최종 계산식은 별도 퀀트 설계에서 승인한다. 계산식 승인 전에는 해당 필드를 생성하거나 `ai_signal_tracker`에 저장하지 않는다.

### 5.7 알림

Slack은 데이터 저장 이후의 독립적인 출력 단계다. 발송 실패는 이미 검증된 데이터베이스 결과를 되돌리지 않는다. 알림에는 실행 ID, 기준 거래일과 데이터 최신 시각을 포함한다. 테스트 환경에서는 실제 Slack 호출 대신 기록 가능한 대체 전송기를 사용한다.

## 6. 전체 데이터 흐름

```text
KRX Open API
  -> 응답 경계 검증
  -> OHLCV 정규화
  -> 종목·거래일 기준 멱등 저장
  -> 최소 20거래일 검사
  -> 14일 ATR 계산 및 저장

Naver 뉴스
  -> 뉴스 정규화와 중복 제거
  -> Gemini 감성 분석
  -> 응답 스키마와 개수 검증
  -> 종목별 OHLCV·ATR 조회
  -> 승인된 결정론적 가격 계산
  -> ai_signal_tracker 멱등 저장
  -> Slack 알림
```

시장데이터 수집 실패는 뉴스 원문 저장을 막지 않는다. 다만 가격 데이터 선행조건을 충족하지 못한 종목은 가격 신호 생성과 `ai_signal_tracker` 가격 필드 저장을 수행하지 않는다.

## 7. 오류 처리와 재처리

오류는 최소한 다음 범주로 구분한다.

- `AUTHENTICATION_ERROR`
- `RATE_LIMITED`
- `NETWORK_ERROR`
- `UPSTREAM_SCHEMA_CHANGED`
- `INVALID_MARKET_DATA`
- `INSUFFICIENT_HISTORY`
- `INVALID_NEWS_DATE`
- `DUPLICATE_NEWS`
- `GEMINI_INVALID_JSON`
- `GEMINI_COUNT_MISMATCH`
- `DATABASE_ERROR`
- `NOTIFICATION_ERROR`

네트워크 오류와 제한 초과는 최대 3회까지 지수 백오프로 재시도한다. 인증 오류, 스키마 변경과 값 검증 오류는 자동 재시도하지 않는다. 부분 성공 시 성공한 종목과 뉴스는 유지하고 실패한 작업 단위만 실행 ID로 재처리한다.

모든 구조화 로그에는 실행 ID, 컴포넌트, 오류 코드, 종목코드 또는 뉴스 식별자, 시각과 재시도 횟수를 포함한다. API 키, 토큰, 전체 Gemini 입력·출력과 개인정보는 포함하지 않는다.

## 8. 검증 전략

### 정적 검사

- 모든 n8n export가 JSON으로 파싱되는지 검사
- 금지된 평문 비밀정보 패턴 검사
- 하드코딩된 과거 기준일 탐지
- workflow가 참조하는 테이블과 저장소 스키마의 일치 여부 검사
- 뉴스가 빈 게시 일시로 DB 노드에 전달되는 경로 탐지
- Gemini 파싱 오류를 조용히 무시하는 코드 탐지

### 단위 테스트

- KRX 정상 응답, 빈 휴장일 응답과 스키마 변경 응답
- 가격과 거래량 경계값
- 중복 종목·거래일
- true range 및 Wilder ATR 정상 계산
- 14개 미만 true range의 부족 상태
- 뉴스 게시 일시 누락과 링크 중복
- Gemini 정상 JSON, 비정상 JSON, 필드 누락과 개수 불일치

### 통합 테스트

- 격리 PostgreSQL에 같은 OHLCV를 두 번 저장해 행 수가 증가하지 않는지 확인
- 같은 `originallink`를 재처리해 중복 행이 생기지 않는지 확인
- 시장데이터 부족 시 가격 신호가 저장되지 않는지 확인
- 알림 실패 시 데이터 저장 결과가 유지되는지 확인
- 비밀정보를 사용하지 않는 비활성 n8n workflow import 검사

### 완료 게이트

`scripts/verify.ps1`은 정적 검사, 단위 테스트와 허용된 통합 테스트를 순서대로 실행하고 하나라도 실패하면 0이 아닌 종료 코드를 반환한다. 운영 성공은 별도의 n8n 실행 기록, PostgreSQL 조회 결과와 Slack 수신 증거가 모두 있을 때만 주장한다.

## 9. Superpowers 적용 정책

- `systematic-debugging`과 `verification-before-completion`은 결함 수정과 완료 보고에 항상 적용한다.
- `brainstorming`은 외부 API 선택, 스키마, 가격 계산식, 여러 workflow에 영향을 주는 변경에 적용한다.
- n8n export와 설정 파일은 일반 코드 TDD의 예외로 승인한다. 대신 변경 전 실패 fixture 또는 정적 검사를 만들고 변경 후 동일 검증을 통과시킨다.
- 구현 계획은 여러 파일 또는 여러 컴포넌트가 관련된 변경에 작성한다.
- git worktree는 최초 기준선 커밋 이후 격리가 필요한 기능 작업에 사용한다.
- 읽기 전용 감사, fixture 분석과 독립 검증은 병렬 에이전트에 위임할 수 있다.
- 동일 파일, 동일 migration 순서 또는 동일 workflow의 구현 작업은 병렬로 수행하지 않는다.

## 10. 에이전트 역할

- 주 에이전트: 범위, 의존 순서, 승인 경계와 최종 통합을 관리한다.
- 시장데이터 에이전트: KRX 계약, OHLCV 정규화와 수집 오류를 담당한다.
- 퀀트·리스크 에이전트: ATR과 승인된 가격 계산식의 수치 검증을 담당한다.
- n8n·DB 에이전트: workflow, PostgreSQL 멱등성, migration과 재처리를 담당한다.
- 독립 검증 에이전트: 요구사항 대조, 회귀 테스트, 보안과 완료 증거를 검토한다.

구현 에이전트의 완료 보고는 독립 검증을 대신하지 않는다. 동시에 실행하는 에이전트는 주 에이전트를 포함해 최대 4개로 제한하며, 쓰기 충돌 가능성이 있으면 직렬 실행한다.

## 11. 구현 순서

1. 저장소 기준선, 문서 지도와 검증 명령을 만든다.
2. 비밀정보를 제거한 n8n export와 검증된 DB 스키마를 편입한다.
3. KRX fixture와 응답 데이터 계약을 만든다.
4. OHLCV 수집·검증·멱등 저장을 구현한다.
5. ATR 계산과 부족 데이터 처리를 구현한다.
6. 뉴스 정제와 Gemini 응답 검증을 보강한다.
7. 승인된 가격 계산식을 별도 설계하고 구현한다.
8. 격리된 n8n·PostgreSQL 통합 테스트를 수행한다.
9. 사용자 승인 후 운영 DB migration과 비활성 n8n import를 수행한다.
10. 운영 증거 확인 후 workflow 활성화와 Slack 발송을 승인받는다.

각 단계는 독립적으로 검증 가능한 결과물을 만들며, 이전 단계의 완료 게이트를 통과하기 전 다음 단계의 운영 반영을 시작하지 않는다.

## 12. 승인 경계

다음 작업은 별도의 사용자 승인 없이 로컬 저장소와 격리 테스트 환경에서 수행할 수 있다.

- 문서, 테스트, fixture와 검증 스크립트 작성
- 비밀정보가 제거된 export와 스키마 스냅샷 관리
- 로컬 단위 테스트와 격리 통합 테스트
- 읽기 전용 에이전트 감사

다음 작업은 실행 직전 사용자 승인이 필요하다.

- 운영 PostgreSQL schema 또는 데이터 변경
- 운영 n8n workflow import, 수정, 활성화와 비활성화
- 실제 Slack 메시지 발송
- KRX 인증정보 저장 또는 권한 변경
- 외부 저장소 push, pull request 병합과 배포

## 13. 성공 기준

하네스의 첫 번째 구현 단계는 다음 조건을 모두 만족할 때 완료된다.

1. 저장소에 문서화된 구조와 단일 검증 명령이 존재한다.
2. n8n export와 DB 스키마가 비밀정보 없이 버전 관리된다.
3. KRX fixture로 OHLCV 정상·경계·오류 경로를 재현할 수 있다.
4. 동일 OHLCV와 동일 뉴스의 재처리가 중복 행을 만들지 않는다.
5. 14일 ATR의 정상값과 부족 데이터 상태가 자동 검증된다.
6. Gemini 오류가 조용히 폐기되지 않는다.
7. OHLCV와 ATR이 없으면 가격 신호를 저장하지 않는다.
8. `scripts/verify.ps1` 전체 검증이 성공한다.
9. 운영 반영 여부와 운영 성공 여부는 로컬 완료 상태와 분리해 보고한다.
